# Setup and usage

## Supported scope

| Component | Source support | Public-release validation |
|---|---|---|
| Client on macOS | AVFoundation capture, local preview, ZeroMQ, WebSocket | Synthetic loopback tested on macOS / Python 3.12 |
| Client on Windows | Default OpenCV capture backend; same Python transport | Syntax reviewed; Windows hardware not tested |
| Client on Linux | Default OpenCV capture backend | Hardware not tested |
| GPU server | NVIDIA CUDA, PyTorch, ONNX Runtime CUDA | Syntax and dependency paths reviewed; full GPU run not repeated |
| Chrome preview | Manifest V3, localhost-only research pages | Packet/scope/safety tests and JavaScript syntax checked |

The desktop client does not require CUDA or an NVIDIA GPU. Full server startup explicitly allocates a CUDA tensor; a macOS-only server or CPU-only setup is not supported by this integration as written. A Linux NVIDIA worker is the intended path. Exact GPU memory and driver requirements depend on the installed models and runtime and have not been established by a public benchmark.

### Hardware planning

| Role | Practical planning target | Important boundary |
|---|---|---|
| Desktop client | Modern 4-core CPU, 8 GB RAM, integrated/USB camera, stable LAN or tunnel | JPEG capture and preview are CPU work; requested resolution/FPS still depend on the camera |
| GPU worker | Linux, CUDA-capable NVIDIA GPU, 16 GB system RAM, 10 GB free disk | No defensible minimum VRAM was established in this release; model/provider compatibility matters more than a guessed number |
| Browser preview | Current Chromium-based browser | Preview panel only; it is not a virtual camera |

These are planning recommendations, not benchmark-derived minimums. The only measured timing in this release is a camera-free local echo test: on an Apple M2 MacBook Air with 8 GB RAM, 30 generated 320×240 frames completed with 0.64 ms average client-reported loopback latency, 1.04 ms p95 and 25.20 effective FPS. That test excludes capture hardware, network travel, detection, model inference, restoration and display, so it must not be used as a face-swap latency claim.

## 1. Install the client

macOS/Linux:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements-client.txt
```

Windows PowerShell:

```powershell
py -3 -m venv .venv
.venv\Scripts\Activate.ps1
python -m pip install -r requirements-client.txt
```

Start with a camera-free transport test:

```bash
python single_image_model/client_core.py --synthetic --loopback --headless --test-frames 30 --width 320 --height 240 --benchmark
```

Expect a final JSON report showing sent and received frames. This verifies transport only. The loopback server uses port 5555 and can choose 5588 if its preferred port is unavailable; the client updates its endpoint for this local test.

## 2. Prepare the GPU worker

Use a separate Python environment, a CUDA-capable NVIDIA GPU, a compatible driver, and a PyTorch build matching your CUDA setup. Install PyTorch following its official installer for the chosen runtime, then:

```bash
python -m pip install -r requirements-server.txt
python -c "import torch, onnxruntime as ort; print(torch.cuda.is_available()); print(ort.get_available_providers())"
```

The first result must be `True`, and the providers must include `CUDAExecutionProvider`. `requirements-server.txt` is an integration starting point, not a verified lockfile. The archived upstream requirements are retained as provenance; they contain differing OpenCV/ONNX pins and should not simply be combined into one environment. Model/native-library compatibility must be resolved for the worker you actually use.

The server imports vendored runtime trees by default. Override `FACE_SWAP_DLC_ROOT` / `FACE_SWAP_FACEFUSION_ROOT` only when intentionally using compatible alternate checkouts. The included runtime versions are Deep-Live-Cam 2.1.5 and FaceFusion 3.9.1 according to their metadata; no original Git commit IDs were available in the source archive.

Obtain the required model weights under their own terms. The helpers locate/download the InsightFace `buffalo_l` pack and InSwapper model; FaceFusion prepares its required detector/mask assets. Model downloads need internet access and disk capacity. Optional CUDA-specific XSeg and FP16 GFPGAN files are not generated by this repository; standard compatible fallbacks may be selected.

## 3. Start the single-image server

Use a source image you own or have permission to process, with one clear face. Supply an **absolute** path because server initialization changes the working directory to the runtime tree.

```bash
python single_image_model/zmq_unified_server.py --source /absolute/private/path/consented-source.jpg --test-only
```

`--test-only` still loads models and runs GPU warm-up; it is not a syntax test. If it completes, remove that flag to run the worker:

```bash
python single_image_model/zmq_unified_server.py --source /absolute/private/path/consented-source.jpg
```

Optional flags: `--onnx-gfpgan` enables available restoration, `--bisenet-region` enables region parsing, and `--mouth-mask` preserves the target's original mouth region. Start without optional stages to simplify troubleshooting.

The default server address is `tcp://127.0.0.1:5555`. This is intentional: the protocol does not authenticate clients. For a remote machine, establish a tunnel from your desktop:

```bash
ssh -N -L 5555:127.0.0.1:5555 user@your-gpu-host
```

Use your own authorized host/account. No cloud credentials are distributed or required in source control.

## 4. Run the desktop client

With the tunnel or local worker ready:

```bash
python single_image_model/client_core.py --server-url tcp://127.0.0.1:5555 --camera-index auto --width 1280 --height 720 --fps 30
```

Grant the Python/terminal application camera permission through your operating system. To choose a known camera, replace `auto` with its integer index. Use `--headless` to disable the local OpenCV preview. Use `--test-frames 300 --benchmark` for a bounded capture run. The client does not synthesize audio or clone voices.

## 5. Local browser demonstration

The browser extension is optional. Its public manifest intentionally limits execution to `http://localhost/*` and `http://127.0.0.1/*`. It displays a floating **Processed video preview** panel with a permanent **DIGITALLY PROCESSED OUTPUT** label.

1. Start the client so its local WebSocket feed is available on port 8765.
2. Open Chrome's extensions manager, enable Developer mode and choose **Load unpacked**.
3. Select the repository's `chrome_extension` directory.
4. Open any local page you control. The preview panel appears and shows the processed stream plus available timing telemetry.
5. Disable or remove the extension when finished.

The extension never requests camera or microphone access, never overrides browser media APIs, and never presents its output as a physical device. It is not a Chrome Web Store release, an OS camera driver, a meeting integration or an interview tool.

## Troubleshooting

- **No CUDA:** confirm the worker has an NVIDIA GPU and matching PyTorch/ONNX Runtime builds; the desktop client may remain on macOS or Windows.
- **Missing models:** inspect model paths and publisher download requirements. Keep weights outside Git.
- **No source face:** use a well-lit, front-facing source image with one face and pass its absolute path.
- **No camera:** check OS privacy permissions; try an explicit index; close apps holding the device. Run synthetic loopback to isolate capture from transport.
- **No returned frames:** verify the worker/tunnel and matching ports; the server requires models and GPU initialization before it listens.
- **No browser preview:** check the local client, port 8765, extension state and localhost origin. Run `node --test chrome_extension/test_extension.js` to verify the public relay contract.
- **Lag:** compare capture, network and inference separately. Reduce capture size or optional stages, then measure. Queue dropping prevents accumulation but cannot eliminate inference/network delay.
